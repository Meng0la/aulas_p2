1 Procedimentos armazenados
(stored procedures)
      Os procedimentos armazenados (do inglês, stored procedures) são
recursos que combinam lógica de programação e comandos SQL.
Segundo Elmasri e Navathe (2018), os procedimentos armazenados são
historicamente conhecidos como módulos armazenados persistentes
(do inglês, persistent stored modules ou SQL/PSM), pelo fato de os códi-
gos estarem armazenados e serem executados pelo SGBD no servidor
de banco de dados. A SQL/PSM pode ser entendida como uma lingua-
gem de programação para banco de dados e que estende a linguagem
SQL por incluir operadores de atribuição, estruturas condicionais e estru-
turas de repetição.

      Características principais dos procedimentos armazenados:

      • São armazenados no banco de dados e podem ser executados por
         aplicações clientes ou por outros procedimentos ou funções.

      • Modularidade, pois permitem construções de módulos pequenos
         e reutilizáveis.

      • Podem ter parâmetros de entrada e saída.

      • Permitem executar operações sobre as tabelas do banco de dados
         como inserções, atualizações e consultas.

      • Permitem instruções de atribuição com operações aritméticas,
         estruturas condicionais e estruturas de repetição.

      Segundo Elmasri e Navathe (2018), os procedimentos armazenados
são úteis nas seguintes situações:

      • Caso o procedimento seja utilizado por várias aplicações, ele pode
         ser armazenado no servidor. Cada aplicação deve apenas realizar

    • Por estar centralizado no banco de dados, as manutenções sobre

         utilizam o procedimento automaticamente refletem a mudança,

    • A execução do procedimento diminui o tráfego de dados entre o
         cliente e o servidor, já que o processamento ocorre no servidor.

    • Os procedimentos também podem permitir a verificação de restri-
         ções complexas que estão além do alcance das asserções e triggers.

    O formato de um procedimento armazenado é dado pelo exemplo 1.

                         Exemplo 1 – Sintaxe para criar procedimento armazenado


   CREATE PROCEDURE <nome do procedimento>(<parâmetros>)
   <corpo do procedimento>;


    Os parâmetros e variáveis locais são opcionais e podem ser declara-
dos, caso seja necessário. Em geral, cada parâmetro deve ser declarado
por um tipo de dado SQL. Além disso, os parâmetros podem ser somente
de entrada, somente de saída ou de entrada e de saída, que são especi-
ficados pela palavra reservada IN, OUT e INOUT, respectivamente. Para
executar um procedimento armazenado utilize a instrução CALL (Silbers-
chatz, Korth e Sudarshan, 2020). O formato de execução da instrução
CALL é apresentado no exemplo 2.

                                 Exemplo 2 – Sintaxe para a instrução CALL


           CALL <nome do procedimento> (<lista de argumentos>);

    Uma instrução condicional em SQL/PSM pode ser utilizada dentro de
uma procedure (Elmasri e Navathe, 2018), a sintaxe é apresentada no
exemplo 8.

                                      Exemplo 8 – Estrutura condicional


  IF <condição> THEN <instruções>
        ELSEIF <condição> THEN <instruções>
        ELSEIF <condição> THEN <instruções>
        ...
        ELSE <instruções>
  END IF;


    O exemplo 8 apresenta a sintaxe da estrutura condicional if, elseif e
else. O comando inicia pela palavra reservada if seguida de uma condi-
ção que possui um valor lógico que pode ser verdadeiro ou falso, seguido
da palavra then. Caso a condição da instrução if seja verdadeira, as ins-
truções serão executadas. Caso contrário, pode ter outras estruturas con-
dicionais definidas pela instrução elseif que também possui condição

      Já o exemplo 9 demonstra uma procedure que utiliza estrutura con-
dicional, para atualizar o bônus do funcionário. O procedimento recebe
o ID do funcionário a quem será aplicado o bônus. Usando o comando
select obtém-se os dados do funcionário. Agora, verifica-se o departa-
mento que o funcionário trabalha. Se for do departamento de TI, tem o
bônus de 10%; caso seja do departamento de vendas, então recebe o
bônus de 15%; de qualquer outro departamento, o bônus é de 5%. No
final, a procedure atualiza o campo salário baseado no bônus recebido.

                        Exemplo 9 – Procedure AplicarBonus()


 CREATE PROCEDURE AplicarBonus (
       IN p_ID INT
 )
 BEGIN
 DECLARE v_Departamento VARCHAR(50);
 DECLARE v_Salario DECIMAL(10,2);

 -- Obtém o departamento e salário atual do funcionário
     SELECT Departamento, Salario INTO v_Departamento, v_Salario
     FROM FUNCIONARIO
     WHERE ID = p_ID;

     -- Estruturas condicionais para aplicar bônus
     IF v_Departamento = ‘TI’ THEN
          SET v_Salario = v_Salario * 1.10; -- 10% de bônus
     ELSEIF v_Departamento = ‘Vendas’ THEN
          SET v_Salario = v_Salario * 1.15; -- 15% de bônus
     ELSE
          SET v_Salario = v_Salario * 1.05; -- 5% de bônus para
 outros
    -- departamentos
 END IF;

    A SQL/PSM oferece alguns tipos de estruturas de repetição como o
while e repeat (Elmasri e Navathe, 2018).

    O exemplo 10 apresenta a sintaxe da estrutura de repetição while.
A instrução começa pela palavra reservada while seguida de uma con-
dição que pode ser um valor lógico, verdadeiro ou falso, seguido da pala-
vra DO. O corpo da instrução de repetição pode incluir diversas instruções
que podem ser repetidas. O fim do comando é marcado pelas palavras
end while. A estrutura de repetição while inicialmente testa a condição,
caso seja verdadeira, ela executa as instruções definidas no bloco de
instruções.

                                     Exemplo 10 – Estrutura de repetição while


                                      WHILE <condição> DO
                                      <instruções>
                                      END WHILE;


    A estrutura de repetição while realiza o teste no início da instrução.
Outra estrutura de repetição pode realizar o teste de condição após a
execução das instruções, como é o caso do comando repeat (Elmasri e
Navathe, 2018). No exemplo 11, o comando executa as instruções e,
somente depois, verifica a condição. Caso a condição seja verdadeira, a
estrutura repete as instruções definidas no bloco de instruções. Caso a
condição seja falsa, o comando avança para o fim do comando de
repetição.

      Suponha uma função que receba o nome do departamento e devolva
o maior salário presente nesse departamento, como descrito no exem-
plo 13:

                  Exemplo 13 – Função MaiorSalarioPorDepartamento()


 CREATE FUNCTION MaiorSalarioPorDepartamento (p_depto VARCHAR(50))
       RETURNS DECIMAL(10,2)
 BEGIN
 DECLARE v_MaiorSalario DECIMAL(10,2);

          SELECT MAX(Salario)
          INTO v_MaiorSalario
          FROM FUNCIONARIO
          WHERE Departamento = p_depto;

          RETURN v_MaiorSalario;
 END;

2 Gatilhos (triggers)
    Um gatilho (ou triggers, do inglês) é um bloco de instruções SQL, pré-
-compiladas e armazenadas no servidor de banco de dados. Esse conjunto
de instruções é executado automaticamente pelo SGBD em resposta a
algum evento que modifique o banco de dados (Elmasri e Navathe, 2018).

    Segundo Elmasri e Navathe (2018), os gatilhos podem ser necessá-
rios em certas condições, que incluem:

    • Monitoração do banco de dados dependendo da regra de
         negócios.

         ◦ Enviar uma mensagem para o supervisor sempre que uma des-
              pesa de funcionário exceder um certo valor limite.

    • Os gatilhos podem implementar algumas restrições de integridade
         que não podem ser implementadas usando a restrição de integri-
         dade do SQL.

         ◦ Pode-se impedir exclusões de funcionários com um cargo espe-
              cífico (ex.: diretor) sem autorização especial.

    • Os gatilhos também podem ser utilizados para auditoria e log de
         mudanças.

         ◦ Manter os registros de operações críticas como exclusões, inser-
              ções ou alteração de algum dado importante.

    Segundo Silberschatz, Korth e Sudarshan (2020), para definir um gati-
lho, deve-se:

    • Definir quando o gatilho deve ser executado. Isto ocorre pelo tra-
         tamento de um evento disparado pelas operações insert, update
         ou delete. Em alguns casos, pode ser necessário definir uma con-
         dição para definir se o gatilho deve ser executado ou não.

      • Especificar a ação, ou seja, qual é o código SQL que dever ser exe-
         cutado para tratar o evento. A ação pode ser executada antes ou
         depois de uma operação de inserção, atualização ou remoção. A
         ação pode verificar e comparar valores antigos e novos para os
         atributos que foram afetados pelo evento que disparou o gatilho,
         para isso, basta utilizar as palavras reservadas OLD e NEW.

      Como exemplo, suponha que se deseje criar um gatilho para registrar
no log de auditoria sempre que um novo funcionário for inserido. Vamos
ao exemplo 14, em que se cria um gatilho de nome auditar_contratacao
que será executado com os dados da tabela FUNCIONARIO. O gatilho exe-
cuta após a inserção de um novo funcionário na tabela FUNCIONARIO, e
executa para cada linha afetada pelo comando de inserção, insere uma
tupla na tabela log_auditoria. O primeiro atributo da tabela log_auditoria
contém a descrição do evento, que neste exemplo é o evento de contrata-
ção de um novo funcionário. O outro atributo é a data do evento. Após isso,
atualiza o atributo data_contratacao da tabela FUNCIONARIO.

                        Exemplo 14 – Trigger auditar_contratacao


 CREATE TRIGGER auditar_contratacao
 AFTER INSERT ON FUNCIONARIO
 FOR EACH ROW
 BEGIN
       -- Inserir no log de auditoria o evento de contratação
       do funcionário
       INSERT INTO LOG_AUDITORIA (descricao, data_evento)
       VALUES (CONCAT(‘Contratação do funcionário ‘, NEW.nome),
       NOW());

          -- Adiciona a data de contratação na tabela de funcionários
          UPDATE FUNCIONARIO
          SET data_contratacao = NOW()
          WHERE NUMAT = NEW.NUMAT;
 END

    Os gatilhos podem trazer alguns efeitos colaterais, como atualizar
tabelas que podem ter, por sua vez, outros gatilhos associados, por exem-
plo. Esse efeito é um cascateamento de chamadas de gatilhos que deve
ser observado e evitado. O cascateamento desses gatilhos pode gerar
um loop recursivo, pelo fato de um evento disparar um gatilho que, por
sua vez, dispara outro gatilho que dispara outro e assim por diante, até
que o último gatilho dispara o primeiro, iniciando novamente a cadeia de
execuções (Ramakrishnan e Gehrke, 2011).


Considerações finais
    Este capítulo apresentou os procedimentos armazenados e as fun-
ções, que são blocos de códigos SQL combinados com instruções de
lógica de programação e que estão pré-compilados e armazenados no
servidor do banco de dados. Esses mecanismos estendem a linguagem
SQL permitindo centralizar alguns tipos de operações, diminuindo o trá-
fego da rede e modularizando algumas regras de negócio, para serem
utilizados em clientes diversos e implementados em diversas linguagens
de programação.

    Em seguida, vimos o conceito de gatilhos, que se constituem também
de blocos de comandos SQL combinados com lógica de programação
e que podem ser executados em resposta a algum evento que modifi-
que o banco de dados, tais como inserção, alteração e remoção. A seção
finaliza com o alerta de evitar o cascateamento de triggers, pois podem
causar efeitos colaterais como o loop recursivo.
